Durable Job Queue

An interactive model of a Postgres-backed job queue that survives worker crashes. Workers claim jobs with FOR UPDATE SKIP LOCKED, hold them under a heartbeated lease, get fenced out when they lose it, and record side effects so a retry never repeats them.

The real code behind each mechanism

The page above is a browser model of the same rules. Here is what enforces them in the actual implementation, and the bug each one prevents.

Claiming without collisions

Prevents: two workers grabbing the same job. Locked rows are skipped instead of waited on, so a pool of workers claims in parallel.

UPDATE jobs SET status = 'running',
       attempts = attempts + 1,
       lease_token = lease_token + 1,
       locked_by = %(worker)s,
       lease_expires_at = now() + %(lease)s
WHERE id = (SELECT id FROM jobs
            WHERE status = 'queued' AND run_at <= now()
            ORDER BY run_at, id
            FOR UPDATE SKIP LOCKED LIMIT 1)
RETURNING *;

Fencing stale workers

Prevents: a frozen worker waking up and overwriting the result of the worker that took over. Try turning fencing off and freezing a worker.

UPDATE jobs SET status = 'succeeded', result = %(result)s
WHERE id = %(id)s
  AND status = 'running'
  AND locked_by = %(worker)s
  AND lease_token = %(token)s;
-- 0 rows updated: we lost the lease, result discarded
jobqueue/store.py · complete(), fail(), heartbeat()

Recovering crashed workers

Prevents: jobs stuck in running forever after a crash. A lost lease counts as an attempt, so a job that keeps killing workers ends up dead instead of looping.

UPDATE jobs SET
  status = CASE WHEN attempts >= max_attempts
           THEN 'dead' ELSE 'queued' END,
  last_error = 'lease expired'
WHERE status = 'running'
  AND lease_expires_at < now();
jobqueue/store.py · reap_expired()

Not repeating side effects

Prevents: a retry sending the same email or charging the same card twice. Try turning the ledger off and killing a worker mid-email.

def once(self, name, fn):
    found, result = store.get_effect(job.id, name)
    if found:
        return result   # an earlier attempt did it
    result = fn()
    store.record_effect(job.id, name, result)
    return result

Idempotent enqueue

Prevents: a client that retries after a timeout creating the same job twice. Same key returns the original job with a 200.

INSERT INTO jobs (type, payload, idempotency_key, ...)
VALUES (...)
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING *;
-- no row back: return the existing job (200)

Proving it

Spec first: 17 acceptance criteria were written before any code, each with its own test. A chaos script then runs the real API and worker processes, sends 650 requests, and kills a worker with SIGKILL mid-run.

PASS 500 jobs stored (150 duplicate enqueues collapsed)
PASS nothing left queued or running
PASS 150 valid emails succeeded
PASS one delivery record per email, none duplicated
PASS 10 invalid emails dead-lettered without retries
PASS jobs from the killed worker were reclaimed (6)

The model uses a 3 second lease so you can watch it expire. The real default is 30 seconds. Each decision behind the design, including the ones that were wrong at first, is written up in DECISIONS.md in the repo.
